# Investment Tracker Production Decision Support v1

## Status

Design approved in chat on 2026-09-10. This specification defines the target state for using Investment Tracker as a primary real-money decision-support system while preserving explicit human approval for every investment action.

## Mission

Build Investment Tracker to a standard where a user can reasonably rely on it as a primary input to investment decisions because every recommendation is reproducible, evidence-backed, risk-constrained, auditable, and capable of abstaining.

The system is **not** an autonomous trading system. It must never place, route, submit, or execute real-money orders. Human approval remains mandatory for every real-world investment action.

The production objective is not "produce more BUY signals." The objective is to produce **trustworthy decisions or trustworthy abstentions** under known evidence, data-quality, portfolio-risk, and operational constraints.

## Production Readiness Definition

Investment Tracker may be called **Production Decision Support v1** only when all hard gates in this specification pass.

A non-official engineering/evidence readiness score of at least **85/100** is necessary but not sufficient. A score above 85 cannot override a failed hard gate.

Official production readiness remains under Independent Audit authority. The system itself, Codex, the coordinator, and workers must never self-promote official maturity or mark official Promotion Gates PASS.

## Non-Goals

Production Decision Support v1 explicitly excludes:

- autonomous order execution;
- brokerage credential storage;
- automatic rebalancing;
- margin, derivatives, leverage, short-selling, or options execution;
- retrospective threshold tuning to improve historical outcomes;
- unlocking replacement holdout symbols without Independent Audit authorization;
- replacing human risk tolerance with inferred or model-generated assumptions;
- promising returns or representing a recommendation as certain.

## Existing Frozen Governance

This design inherits and must preserve the existing tracker governance:

- `TPC-v1.2`
- `REPLAY-v1.0`
- `CALC-v1.2`
- `ROBUST-v1.0`
- paper-only historical/prospective validation;
- Phase A / Phase B partitioning;
- C24 censoring boundaries;
- no same-close execution;
- t+1 open execution for historical episodes;
- exact-timing SPY comparison;
- range quarantine propagation;
- `max_drawdown` remains UNKNOWN while DQ-030 is unresolved;
- missing required evidence means UNKNOWN / ABSTAIN;
- `STRONG ENTRY` is never created from price-only evidence;
- the contaminated original holdout cannot be used as clean evidence;
- replacement holdout symbols `HACK`, `SOXX`, `NLR`, `URNM`, `GEV` remain locked until Independent Audit explicitly authorizes release.

No production-readiness work may weaken these constraints.

## Decision-Support Contract

Every user-facing investment assessment must return a structured decision record. The record must separate the underlying frozen signal from the higher-level recommendation.

Required fields:

```text
decision_id
asset
as_of_timestamp
market_data_cutoff
signal_state
recommendation_state
confidence_level
confidence_basis
portfolio_risk_status
max_policy_allocation
current_policy_allocation
incremental_policy_room
rationale
contrary_evidence
invalidators
relevant_dq_refs
source_snapshot_id
calculation_version
recommendation_version
decision_status
human_approval_required
```

### Signal State

`signal_state` remains the frozen replay/state-machine output. It must not be rewritten to make the recommendation more attractive.

### Recommendation State

The production recommendation layer may emit only:

- `CONSIDER_ACCUMULATING`
- `HOLD_OFF`
- `CONSIDER_TRIMMING`
- `NO_ACTION`
- `ABSTAIN`

Recommendation mapping must be deterministic, versioned, tested, and frozen before out-of-sample evaluation of that recommendation version.

The recommendation layer may be stricter than the signal layer. For example, an ACCUMULATE signal may still become `ABSTAIN` or `NO_ACTION` because of stale data, unresolved DQ, portfolio concentration, insufficient evidence, or an operational control failure.

It may never be looser than hard governance or risk constraints.

### Human Approval

`human_approval_required` must always be `TRUE` for real-money use in v1.

No output generated by this repository may be treated as an order instruction consumable by a brokerage API.

## Confidence Model

Confidence must not be an LLM intuition score.

It must be derived from explicit evidence dimensions. At minimum:

- canonical data completeness;
- benchmark alignment completeness;
- absence/presence of unresolved DQ affecting the decision;
- historical sample breadth across independent assets;
- episode count rather than repeated daily-signal count;
- robustness consistency across regimes;
- out-of-sample Phase B consistency;
- prospective paper evidence;
- operational health;
- portfolio-risk-policy completeness.

Allowed confidence values:

- `LOW`
- `MEDIUM`
- `HIGH`
- `UNAVAILABLE`

`HIGH` must require all decision-critical evidence dimensions to meet their frozen minimums. Missing a critical dimension forces `UNAVAILABLE` and therefore recommendation `ABSTAIN`.

The confidence formula and thresholds must be versioned before prospective production evaluation and may not be changed based on subsequent realized performance without a new governed version.

## Mandatory Abstention Conditions

The system must fail closed and emit `ABSTAIN` when any of the following apply:

- required market data is missing or stale beyond the governed freshness window;
- exact benchmark alignment required by the calculation is missing;
- a decision-critical DQ issue is unresolved;
- canonical input digests fail verification;
- the worker snapshot is stale versus canonical state;
- frozen version strings do not match;
- calculation-test suite is not fully passing;
- portfolio risk policy is missing, ambiguous, or cannot be evaluated;
- recommendation would violate an approved portfolio risk limit;
- operational health indicates alerting, data ingestion, or validation may be impaired;
- evidence breadth is below the minimum production gate;
- a requested symbol is in the locked holdout;
- inputs include contaminated holdout evidence not permitted by governance;
- two independent validation paths materially disagree and the disagreement is unresolved.

Abstention is considered correct system behavior, not a failure to provide an answer.

## Portfolio Risk Layer

A production decision cannot be generated from asset-level signal quality alone.

The recommendation engine must read the canonical `Portfolio Risk Policy` and current `Portfolio Snapshot` before producing any allocation-sensitive recommendation.

The repository must not invent risk tolerance or default monetary allocations when the canonical policy is absent.

Until an approved Portfolio Risk Policy supplies deterministic limits, the system may discuss signal quality but must set allocation fields to unavailable and must not issue a position-sizing recommendation.

At minimum, the governed policy must be capable of expressing:

- maximum single-position exposure;
- maximum theme/sector exposure;
- maximum correlated-proxy exposure;
- maximum aggregate risk exposure;
- minimum liquidity/cash buffer if applicable;
- concentration restrictions;
- conditions that force trim/no-add decisions;
- portfolio drawdown response once a deterministic drawdown convention is formally defined and tested;
- explicit treatment of unknown portfolio values.

Portfolio constraints always override a favorable asset signal.

## Recommendation Rationale

Every non-ABSTAIN recommendation must contain:

1. the frozen signal state and key gate outcomes;
2. evidence supporting the recommendation;
3. contrary evidence or weaknesses;
4. portfolio-risk constraints that affected the result;
5. exact data timestamp/cutoff;
6. relevant DQ references;
7. conditions that would invalidate or change the recommendation.

The rationale must be generated from the structured decision record. Narrative text may explain a decision but must not create facts that are absent from the record.

## Historical Evidence Gate — Phase A

Phase A is not complete until every required proxy reaches `BASELINES_COMPLETE` under frozen rules.

Required proxies:

- ETN
- PWR
- VRT
- URA
- CIBR
- SMH
- COPX
- XLE

For every proxy, the canonical evidence chain must include:

```text
canonical market data
 -> Replay Daily
 -> unique episodes
 -> horizon outcomes
 -> SPY / cash comparisons
 -> friction scenarios
 -> range quarantine handling
 -> C17 buy-and-hold baseline
 -> C18 monthly DCA baseline
 -> C19 simple-dip baseline
```

All stage transitions must follow the canonical Phase Matrix state machine and require persistence plus readback before advancement.

Historical evidence must report both signal-day counts and unique-episode counts. Repeated overlapping daily observations must not be presented as independent evidence.

## Robustness Gate

`ROBUST-v1.0` must be executed after full required Phase-A breadth is frozen.

The robustness report must include at minimum:

- per-asset performance dispersion;
- regime sensitivity;
- horizon sensitivity;
- friction sensitivity at the frozen scenarios;
- episode/non-overlap sensitivity;
- dependence/overlap disclosure;
- block/bootstrap sensitivity where technically meaningful;
- concentration of gains in a small number of episodes;
- baseline-relative results;
- downside/negative-tail behavior;
- stability of conclusions when one proxy is removed at a time.

A production PASS requires evidence that the tracker is not dependent on one asset, one market regime, one horizon, or a handful of overlapping episodes.

Codex must not tune frozen entry rules in response to this analysis. Weak robustness is a failed/limited result, not an invitation to optimize the historical sample.

## Independent Recalculation Gate

A separate validation path must recompute the material historical results from canonical inputs.

This path should share schemas and frozen specifications but should not reuse the same high-level calculation functions whose outputs it is auditing.

It must independently validate at least:

- indicators and gates;
- state precedence;
- episode starts;
- t+1 entry dates/open prices;
- horizon dates;
- asset returns;
- exact-timing SPY returns;
- cash hurdle;
- friction deductions;
- C24 censoring;
- quarantine propagation;
- baseline outputs.

Any unexplained material disagreement blocks production readiness.

## Candidate Freeze Gate

After Phase A and robustness pass, the complete candidate must be frozen before Phase B evaluation.

The freeze record must include:

- calculation versions;
- recommendation version;
- confidence methodology;
- all thresholds;
- portfolio-risk interpretation rules;
- DQ handling;
- exact asset universe;
- benchmark rules;
- baseline rules;
- censoring rules;
- prospective protocol;
- code commit SHA;
- canonical Sheet snapshot digests.

Any substantive post-freeze change creates a new candidate version and invalidates direct comparison as the same candidate.

## Phase B Out-of-Sample Gate

Phase B must be run strictly with the frozen candidate and no retrospective tuning.

Phase B date boundary remains governed by the canonical tracker. Horizons crossing the frozen Phase-B end date must be censored rather than matured with later data.

The report must compare Phase B behavior with:

- Phase A expectations;
- SPY;
- cash hurdle;
- frozen baselines;
- risk and abstention behavior;
- asset/regime dispersion.

Production readiness requires that Phase B does not reveal a material breakdown in the premise supporting the candidate.

A weak or adverse Phase B result must remain visible; it cannot be repaired by silently modifying thresholds and re-labeling the run as the same candidate.

## Replacement Holdout Gate

The replacement holdout symbols remain inaccessible until Independent Audit authorizes release after the prerequisite frozen gates have passed.

Programmatic enforcement must prevent provider requests, cache inspection, inference, summaries, or derived statistics for:

- HACK
- SOXX
- NLR
- URNM
- GEV

When eventually authorized, holdout evaluation must be performed once under a frozen candidate and fully logged.

Codex must treat accidental holdout access as a contamination incident requiring DQ evidence and governance review.

## Prospective Paper Validation Gate

Historical validation alone is insufficient for production real-money decision support.

The tracker must operate prospectively in paper mode using information available at the time each decision is generated.

Minimum target before Production Decision Support v1 approval:

- at least **20 unique meaningful decision episodes**;
- target **20–30 episodes** before relying materially on the prospective result;
- evidence must span more than one market environment;
- no retroactive changes to recorded recommendations;
- immutable snapshot of each decision input;
- timestamped recommendation record;
- outcome tracking using the frozen prospective protocol;
- explicit record of every ABSTAIN and its reason;
- no deletion of adverse recommendations or losing episodes.

A dedicated `Prospective Protocol` must be versioned before these episodes count toward the production gate. It must define what constitutes a unique episode and how market environments/regimes are classified without hindsight.

Until that protocol is frozen, prospective observations may be collected but cannot be counted as production qualification evidence.

## Operational Reliability Gate

Production decision support must be reliable even when calculations are correct.

Required controls include:

- monitored market-data ingestion;
- stale-data detection;
- deterministic retry/failure handling;
- alert-delivery health checks;
- explicit alert delivery acknowledgement or failure evidence;
- startup verification of frozen versions and calculation tests;
- immutable run IDs and evidence references;
- canonical write serialization;
- post-write readback verification;
- recovery procedures for interrupted writes;
- backup/export procedure for canonical evidence;
- reproducible rebuild from source evidence;
- structured logging without credentials;
- health status surfaced to the recommendation engine.

Known alert-delivery/control gaps must be resolved before a production PASS.

If operational health is degraded in a way that can make the decision stale or unverifiable, recommendations must automatically degrade to `ABSTAIN`.

## Security Gate

The production repository and runtime must enforce least privilege.

Requirements:

- no API keys, OAuth tokens, service-account keys, brokerage credentials, or connector tokens in GitHub;
- workers cannot mutate the canonical Sheet;
- only the coordinator runtime may hold canonical Sheet write capability;
- locked-holdout denial occurs before provider requests;
- secrets are injected through approved runtime secret storage;
- logs redact credentials and sensitive connector metadata;
- dependencies are pinned or constrained and scanned;
- CI cannot expose production secrets to untrusted PR code;
- recommendation generation does not require brokerage credentials.

## Adversarial / Failure Testing Gate

Production tests must prove that the tracker fails safely.

At minimum, automated tests must cover:

- stale market data;
- missing sessions;
- duplicate dates/keys;
- malformed source digests;
- conflicting provider evidence;
- unresolved DQ;
- formula-backed canonical values where static evidence is required;
- incorrect split normalization;
- exact-threshold floating-point boundaries;
- same-close execution attempts;
- Phase A / Phase B leakage;
- C24 boundary crossings;
- accidental locked-holdout request;
- stale worker snapshots;
- concurrent canonical writers;
- stale canonical write lock;
- partial canonical write;
- failed post-write readback;
- incorrect Phase Matrix transition;
- recommendation despite missing portfolio policy;
- recommendation that exceeds risk policy;
- degraded operational health;
- zero-evidence worker submission;
- narrative text contradicting structured decision fields.

A test suite that only proves the happy path is insufficient.

## Engineering/Evidence Readiness Score

The repository may compute a non-official engineering/evidence score to track progress. The scoring weights must be frozen before they are used for promotion decisions and may not be adjusted to manufacture an 85+ result.

Recommended v1 weighting:

| Domain | Points |
| --- | ---: |
| Historical Phase-A breadth and arithmetic integrity | 20 |
| Robustness and dependence analysis | 15 |
| Phase-B out-of-sample evidence | 15 |
| Prospective paper evidence | 15 |
| Portfolio-risk controls | 10 |
| Data quality / independent reconciliation | 10 |
| Operational reliability / monitoring / recovery | 10 |
| Governance and independent audit readiness | 5 |
| **Total** | **100** |

Hard-gate failures cap readiness regardless of arithmetic score.

Recommended caps:

- incomplete required Phase A: maximum 69;
- robustness not passed: maximum 74;
- Phase B not passed: maximum 79;
- prospective paper gate incomplete: maximum 84;
- unresolved critical operational, security, portfolio-risk, or audit blocker: maximum 84;
- Independent Audit not passed: system cannot be labeled Production Decision Support v1 regardless of score.

These caps prevent infrastructure or historical backtest depth from substituting for missing real-world evidence.

## Production Hard Gates

The system may be proposed to Independent Audit for Production Decision Support v1 only when all are true:

1. Required Phase-A proxies are `BASELINES_COMPLETE`.
2. Phase-A arithmetic and lineage audits have no unresolved critical discrepancy.
3. `ROBUST-v1.0` has passed the frozen acceptance criteria.
4. Independent recalculation materially agrees with canonical evidence.
5. Candidate rules and code are frozen before Phase B.
6. Phase B has completed strictly out-of-sample and passed its acceptance criteria.
7. Holdout governance has no unauthorized access incident, or any incident has been explicitly adjudicated.
8. Prospective paper protocol is frozen and its minimum evidence target is satisfied.
9. Portfolio Risk Policy and Portfolio Snapshot integration are complete and tested.
10. Alerting/monitoring/recovery controls are operational and tested.
11. Security and least-privilege controls pass.
12. Adversarial/failure suite passes.
13. Engineering/evidence score is at least 85/100.
14. No open critical DQ or control gap can invalidate current recommendations.
15. Independent Audit explicitly approves Production Decision Support v1.

Failure of any single hard gate prevents production designation.

## Recommendation Release Stages

### Stage 0 — Historical Research

Current-style historical validation. No live recommendation reliance.

### Stage 1 — Prospective Observation

Generate timestamped paper recommendations. User may view them, but the system explicitly labels itself unqualified for real-money reliance.

### Stage 2 — Shadow Decision Support

Tracker produces the same complete decision record intended for production, but user decisions are not expected to follow it. Compare recommendations with actual later outcomes and record all abstentions/failures.

### Stage 3 — Production Decision Support v1

Allowed only after all hard gates and Independent Audit pass.

The tracker may then be used as a primary input to human investment decisions. Every record still requires human approval and remains subject to portfolio policy and abstention controls.

### Stage 4 — Autonomous Execution

Out of scope for this specification. Reaching Stage 3 does not authorize Stage 4.

## Codex Execution Objective

Codex should optimize for **trustworthiness, falsifiability, reproducibility, and failure-safe behavior**, not for maximizing historical returns or recommendation frequency.

The implementation sequence should prioritize:

```text
finish/stabilize tracker-framework-v1
 -> finish required Phase A breadth
 -> independent reconciliation
 -> ROBUST-v1.0
 -> freeze candidate
 -> Phase B out-of-sample
 -> prospective protocol and paper observation
 -> portfolio decision layer
 -> operational/security hardening
 -> adversarial test program
 -> readiness scoring
 -> Independent Audit package
```

Codex may parallelize independent asset workers and read-only audits, but canonical Google Sheet writes remain coordinator-only and serialized.

## Definition of Done for Codex

Codex is not done when tests are green or when the score displays 85.

Codex is done with the Production Decision Support v1 engineering program when it can produce an audit package containing:

- exact code commit and dependency state;
- frozen configuration/rule versions;
- canonical Sheet snapshot digests;
- Phase Matrix evidence;
- complete DQ and Run Ledger lineage;
- Phase-A summary by asset/horizon/baseline;
- robustness report;
- independent recomputation report;
- candidate freeze record;
- Phase-B report;
- prospective-paper report;
- portfolio-risk-policy test report;
- operational reliability test report;
- security/least-privilege report;
- adversarial/failure test report;
- engineering/evidence score breakdown;
- unresolved risks and limitations;
- explicit statement that real-money actions still require human approval.

The final package must make negative findings as easy to inspect as positive findings.

## Acceptance Principle

The tracker earns trust by showing when it **does not know**, by preserving adverse evidence, and by making every decision reproducible.

A system that is highly confident but cannot demonstrate lineage, robustness, out-of-sample behavior, prospective evidence, portfolio constraints, and operational reliability is not production decision support.
