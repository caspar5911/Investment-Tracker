# Investment Tracker Multi-Agent Architecture

## Status

Design approved in chat on 2026-09-10. This document defines how Codex agents may work in parallel without corrupting the canonical Investment Tracker evidence chain.

## Goal

Use GitHub/Codex for parallel engineering and validation work while preserving the existing Google Sheet as the canonical control plane and evidence store. Parallel workers may prepare, compute, validate, and review isolated work products, but exactly one coordinator owns canonical mutations.

## Source-of-Truth Model

### GitHub

GitHub is the source of truth for:

- agent instructions and role definitions;
- executable validation/replay code;
- tests and regression checks;
- versioned schemas and frozen calculation rules mirrored from the control plane;
- staging artifacts generated by workers;
- audit reports, implementation notes, and reproducibility metadata.

### Google Sheet

The existing Google Sheet remains the canonical evidence/control plane for:

- Canonical Spec;
- Calculation Conventions;
- Calculation Tests;
- Robustness Protocol;
- Phase Matrix;
- Market Data;
- Replay Daily;
- Replay Episodes;
- Data Quality;
- Promotion Gates;
- Automation Registry;
- Run Ledger;
- Baseline Results.

No GitHub artifact is allowed to silently supersede a canonical Sheet record.

## Frozen Governance Constraints

The agent system must preserve these project constraints:

- Paper-only validation. No trade execution.
- Frozen versions: `TPC-v1.2`, `REPLAY-v1.0`, `CALC-v1.2`, `ROBUST-v1.0` unless a separately approved, versioned governance change is introduced.
- Historical rule thresholds must never be tuned in response to observed outcomes.
- Phase A and Phase B boundaries must remain hard partitions.
- The original temporal holdout is contaminated and cannot be treated as clean evidence.
- Replacement holdout symbols `HACK`, `SOXX`, `NLR`, `URNM`, and `GEV` remain locked. Workers must not fetch, inspect, summarize, infer, or use their historical data until Independent Audit authorizes access.
- `STRONG ENTRY` is never generated from price-only replay.
- Missing or ambiguous required evidence means `UNKNOWN` / `ABSTAIN`, not inference.
- `max_drawdown` remains `UNKNOWN` until its deterministic convention is explicitly versioned and tested. Existing DQ-030 governs this gap.
- Only Independent Audit can mark Promotion Gates PASS or change official maturity/readiness.
- Engineering/evidence readiness estimates may be reported separately but must never be represented as official production readiness.

## Architecture

The system uses a coordinator plus isolated workers.

```text
                         +----------------------+
                         |   Codex Coordinator  |
                         | single canonical     |
                         | writer               |
                         +----------+-----------+
                                    |
              review / validate / merge only
                                    |
      +-----------------------------+-----------------------------+
      |                             |                             |
+-----v------+                +-----v------+                +-----v------+
| Worker A   |                | Worker B   |                | Worker C   |
| URA        |                | CIBR       |                | SMH        |
| isolated   |                | isolated   |                | isolated   |
+------------+                +------------+                +------------+
      |                             |                             |
      +-----------------------------+-----------------------------+
                                    |
                         +----------v-----------+
                         | Worker D             |
                         | COPX / XLE           |
                         +----------------------+
                                    |
                         +----------v-----------+
                         | Worker E             |
                         | audit / robustness   |
                         | read-only canonical  |
                         +----------------------+
```

The key rule is that workers do not directly mutate canonical Sheet tabs. They produce deterministic staging outputs plus validation manifests. The coordinator verifies those outputs and is the only role permitted to perform canonical writes.

## Agent Roles

### Coordinator

Responsibilities:

- read startup control-plane tabs before each integration run;
- verify exact frozen versions and calculation-test status;
- allocate non-overlapping worker scopes;
- verify workers did not access locked holdout symbols;
- compare staging output against canonical schema and frozen rules;
- perform the only writes to canonical Sheet tabs;
- read back every canonical mutation before declaring it complete;
- append Data Quality and Run Ledger records for defects, repairs, and integration runs;
- update Phase Matrix only after evidence is persisted and validated;
- leave Promotion Gates unchanged unless an Independent Audit action explicitly authorizes a change.

The coordinator must fail closed on ambiguity.

### Worker A — URA

Scope:

- complete URA Phase-A cache for remaining years;
- build URA Replay Daily;
- derive unique ACCUMULATE episodes;
- compute outcomes for 1/5/20/60/120/250 trading-day horizons;
- compute SPY/cash/friction comparisons;
- apply range quarantine propagation to MAE/MFE;
- compute frozen C17/C18/C19 baselines;
- emit staging data and validation manifest.

### Worker B — CIBR

Same full Phase-A pipeline as URA, isolated to CIBR plus the already-canonical SPY benchmark.

### Worker C — SMH

Same full Phase-A pipeline, with explicit verification of the known 2:1 split effective 2023-05-05 and `NORM-v1` normalization for pre-split prices.

### Worker D — COPX / XLE

Complete COPX first, then XLE. XLE must retain awareness of its verified 2025 split rule even though Phase A ends in 2023 so normalization logic remains deterministic and future Phase-B processing cannot drift.

### Worker E — Audit / Robustness

Read-only against canonical evidence. Responsibilities:

- independent arithmetic recomputation;
- duplicate/session/key/digest checks;
- t+1 execution verification;
- C24 partition checks;
- dependence/overlap diagnostics;
- ROBUST-v1.0 preparation and later execution;
- cross-asset comparison;
- identification of evidence gaps and regression failures.

Worker E must never repair canonical evidence itself; findings are returned to the coordinator.

## Worker Isolation

Each worker operates in a dedicated branch or worktree and writes only to its own staging namespace.

Recommended branch names:

- `agent/ura-phase-a`
- `agent/cibr-phase-a`
- `agent/smh-phase-a`
- `agent/copx-xle-phase-a`
- `agent/audit-robustness`

Workers must not edit another worker's staging files.

## Staging Contract

Each worker must output:

```text
staging/<worker>/<run-id>/
  manifest.json
  market-data.csv
  replay-daily.csv
  replay-episodes.csv
  baseline-results.csv
  validation.json
  dq-candidates.json
  notes.md
```

Files that do not apply to a worker run are omitted rather than filled with fake rows.

### `manifest.json`

Must contain:

- worker role;
- run ID;
- asset scope;
- exact date scope;
- frozen version strings;
- source provider/feed;
- input canonical evidence references;
- output file digests;
- locked-holdout access assertion;
- completion status.

### `validation.json`

Must include deterministic counts and invariants such as:

- expected/fetched/persisted sessions;
- unique dates;
- unique canonical keys;
- malformed digest count;
- benchmark date mismatches;
- close/range usable counts;
- signal-state distribution;
- episode-start count;
- horizon counts;
- friction counts;
- matured/censored counts;
- quarantine-propagation counts;
- arithmetic mismatch counts.

A worker may mark its staging run `READY_FOR_COORDINATOR_REVIEW`; it may not mark a canonical phase complete.

## Canonical Integration Protocol

For each worker submission the coordinator must perform the following sequence:

1. Re-read startup control tabs and verify frozen versions.
2. Verify the worker manifest and file digests.
3. Verify asset/date scope is authorized.
4. Verify no locked holdout symbol appears in any input/output/log.
5. Re-run deterministic validation locally or independently.
6. Compare session dates against canonical SPY using asset/date/status logic, never physical row-position assumptions.
7. Persist one bounded canonical block.
8. Read that block back.
9. Freeze formulas to static values when the canonical schema requires static evidence.
10. Run post-freeze invariants.
11. Append DQ evidence if any defect was detected or repaired.
12. Append Run Ledger evidence.
13. Update Phase Matrix last.
14. Re-read Phase Matrix and the relevant evidence endpoints.

If any step fails, the coordinator stops that asset/year at its previous canonical state.

## Write Lock

Canonical Google Sheet writes are serialized through a logical lock owned by the coordinator.

A mutation run must have a unique run ID and must not overlap another canonical mutation run. Worker computation can remain parallel because it does not own the canonical lock.

A future executable implementation should enforce this with a lock file/state record, for example:

```text
.runtime/canonical-write-lock.json
```

The lock record should contain coordinator run ID, acquired timestamp, scope, and expected release condition. Stale locks must never be silently broken; they require an explicit recovery path and DQ record.

## Market Data Rules

Workers and coordinator must preserve the established cache protocol:

- one symbol per provider request;
- full year first for later years;
- on 5xx retry exactly once at the same scope;
- then fall back to quarter and month if required;
- no provider substitution for canonical history;
- independent sources may corroborate anomalies but never silently replace Alpaca raw data;
- persist/read back a clean fetched window before advancing;
- identical active key + identical raw means reuse;
- changed raw means append a superseding record plus DQ evidence, never overwrite without lineage.

`bar_key` remains:

```text
ASSET|YYYY-MM-DD|ALPACA_SIP|NORM-v1
```

## Replay Rules

Executable code must implement the frozen replay methodology exactly, including:

- signal on completed day-t close;
- execution at next trading session t+1 open;
- consecutive ACCUMULATE days collapse into one episode;
- entry is tied to the first ACCUMULATE signal, not episode end;
- Phase-A horizons crossing 2023-12-31 are censored;
- Phase-B horizons crossing 2025-09-07 are censored;
- SPY uses the same entry trading date and exact same horizon close date;
- range quarantine affects MAE/MFE, not otherwise-verified close returns;
- friction scenarios are 0/10/25 bps total round-trip;
- cash hurdle is 3.25% annualized using elapsed calendar days;
- overlapping observations are not treated as independent N.

## Baselines

Every evaluated proxy must include frozen comparisons against:

- C17 buy-and-hold;
- C18 equal-notional monthly DCA at the first trading-session open of each month;
- C19 simple dip: close <= 90% of prior-60-day high, deduplicated into episodes and executed with the same t+1/horizon conventions.

Baseline results may not be redefined after seeing tracker outcomes.

## Robustness Boundary

Workers may prepare robustness inputs while Phase A is incomplete, but `ROBUST-v1.0` execution that depends on full breadth should not be considered complete until all required Phase-A proxies are frozen through baselines.

Robustness output must disclose:

- asset/theme concentration;
- regime sensitivity;
- horizon sensitivity;
- friction sensitivity;
- repeated-signal dependence;
- episode/non-overlap sensitivity;
- block/bootstrap sensitivity where feasible;
- baseline-relative performance.

## Failure Handling

### Provider failure

Follow the frozen retry/fallback protocol. Do not switch canonical provider.

### Missing benchmark alignment

Mark the affected calculation `UNKNOWN` and stop canonical promotion of that block until reconciled.

### Worker disagreement

The coordinator does not average or vote. It reproduces the disputed invariant and either resolves it deterministically or records a DQ gap.

### Canonical write defect

Do not hide the defect. Preserve the erroneous lineage where necessary, repair with deterministic evidence, append a DQ record, and close through a new reconciliation run.

### Formula error

No canonical state is considered frozen until formula-backed staging output is read back, validated, converted to static values where required, and read back again.

## Security and Secrets

No API key, credential, OAuth token, service-account secret, or connector token may be committed to GitHub.

Repository configuration must use environment-variable names and example files only. Runtime credentials remain in Codex/connector secret storage.

## Testing Strategy

The implementation must provide automated tests for at least:

- frozen version enforcement;
- holdout symbol denial;
- one-symbol provider requests;
- retry/fallback sequencing;
- canonical key construction;
- digest canonicalization;
- native trading-date handling;
- split normalization;
- exact SPY date alignment;
- replay gates and state precedence;
- episode deduplication;
- t+1 open execution;
- C24 censoring;
- cash hurdle arithmetic;
- friction arithmetic;
- MAE/MFE quarantine propagation;
- baseline definitions;
- single-writer lock behavior;
- Phase Matrix transition ordering;
- failure-closed behavior for missing evidence.

Integration tests should use deterministic fixtures and must not require access to the locked holdout.

## Phase-Matrix State Machine

The code should enforce the existing progression:

```text
VALIDATED_NOT_CACHED
  -> PARTIAL_CACHE
  -> CACHED_CLEAN / QUARANTINED
  -> REPLAY_DAILY_COMPLETE
  -> EPISODES_COMPLETE
  -> OUTCOMES_COMPLETE
  -> BASELINES_COMPLETE
```

Transitions may advance only after canonical evidence is persisted and independently read back. Regressions are allowed only through explicit reconciliation with DQ/Run Ledger evidence.

## Score Governance

The repository may compute an engineering/evidence readiness estimate, but it must label that value as non-official.

The implementation must never:

- write an official maturity promotion;
- mark a Promotion Gate PASS on its own;
- represent a working engineering score as the audited Production Readiness score.

Independent Audit retains authority for official maturity and readiness.

## Initial Delivery Scope

The first implementation milestone will create:

- root `AGENTS.md` with project-wide safety and governance rules;
- role-specific agent instruction files;
- typed configuration for assets, versions, boundaries, and locked holdout;
- canonical schemas for Market Data, Replay Daily, Replay Episodes, Baseline Results, DQ candidates, and manifests;
- a worker staging contract;
- deterministic validation library;
- single-writer coordinator lock/integration layer;
- unit and integration tests;
- a CLI entry point suitable for Codex workers and coordinator use;
- documentation describing how to launch isolated workers and integrate their results.

The first implementation milestone will not execute trades, unlock holdouts, alter frozen rules, or change official Promotion Gates.

## Success Criteria

The architecture is ready for production-style historical validation when all of the following are true:

1. Multiple Codex workers can compute independent asset scopes concurrently without sharing writable canonical state.
2. Only the coordinator can perform canonical Sheet mutations.
3. Every worker result is deterministic and self-describing through a manifest and validation report.
4. Locked holdout access is programmatically denied.
5. Canonical writes are read back and verified before Phase Matrix advancement.
6. Data-quality defects create explicit lineage rather than being silently repaired.
7. Full automated tests prove replay, execution, censoring, normalization, quarantine, and baseline conventions.
8. Existing tracker evidence can be reproduced without changing frozen rules.
